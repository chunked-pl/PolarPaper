# PolarPaper — Scanner 4/5: Speed & Threading Architecture Audit

Scope: all `.java` files under `core/`, `src/`, `paper_latest/`, `paper_1_21_11/`, `paper_26_1_2/`. Focus: main-thread stalls, threading correctness, save/load pipeline throughput, startup/shutdown behaviour. No source files were modified.

Severity legend: **CRITICAL** = user-visible freeze/corruption risk in normal operation; **HIGH** = real stall/starvation under common usage; **MEDIUM** = measurable waste or race with narrow trigger; **LOW** = polish.

Context that matters for every finding below: Bukkit **main thread is sacred**. Autosave runs as a sync timer task (`Polar.startAutoSaveTask` → `runTaskTimer`), so everything the save pipeline does synchronously lands on the main thread. `TaskFutures.runSync` executes **inline when already on main** (`TaskFutures.java:27-32`) — correct for consistency, but it means callers silently absorb full-cost loops on main.

## B. Detailed findings

### B1. Main-thread stalls

- `src/main/java/live/minehub/polarpaper/commands/PasteCommand.java:109-136` | **CRITICAL** | Command executes on main thread and does: `Files.readAllBytes(path)` (sync IO), `PolarReader.read(polarBytes)` (full Zstd decompress + parse of every section), then `Schematic.paste` → `pasteSection` loops 4096 blocks × sections calling `BlockUtil.setBlockFast` individually. No staging. | Multi-second freeze for even modest schematics (a 64×64-chunk paste ≈ 16.8 M block writes); all players frozen, watchdog warnings. | Load+parse off-thread via `TaskFutures.runAsync`; write blocks in batched tasks spread over ticks, or reuse this plugin's own proven pattern: build `LevelChunkSection`s off-thread and swap them per-chunk like `replaceChunkBlocks` (`PolarStreamLoader.java:343-367`). At minimum batch per-section writes instead of per-block holder lookups.

- `core/.../world/PolarWorld.java:286-294` + `core/.../util/TaskFutures.java:27-32` + `core/.../world/PolarChunk.java:231-243` | **HIGH** | `convert()` builds its future list by calling `PolarChunk.convert` immediately; for every already-loaded chunk `runSync` completes inline, so the **entire snapshot pass** (storage-array clones per section, block-entity NBT serialization, entity listing, heightmap copies — `snapshotChunk:278-334`) runs as one uninterrupted burst on the main thread at the moment a save starts. Only `buildChunk` is off-thread. | The dominant per-autosave main-thread cost: ~50–200 µs/chunk ⇒ hundreds of ms spike on large worlds, every interval. This is exactly the "large loop over chunks executed sync" anti-pattern; Paper itself amortizes chunk saves across ticks. | Amortize: schedule snapshot tasks K chunks per tick (queue drained over N ticks), or snapshot only dirty chunks (see B3). The two-phase design is right — the phases just need to be spread.

- `src/main/java/live/minehub/polarpaper/PolarPaper.java:76-118` | **MEDIUM-HIGH** | `onDisable`: sequential `saveWorldSynchronously(world)` per world (full convert + Zstd compress + file write, all sync), plus `Files.walk(...).forEach(File::delete)` recursive delete of each world folder, all on main thread. Also no guard against an async autosave still in flight (`AUTOSAVE_TASK_MAP` cancelled but `saveInProgress` not awaited) — shutdown save and in-flight async save can both write the same file. | Shutdown stall grows linearly with worlds×size (multi-second to minutes). Race yields last-writer-wins (both snapshots valid, but archive `bindSource` swap interleaves). | Await in-flight saves before disabling (track futures per world), skip the folder walk when nothing to clean, and document/pipeline the sequential saves. Incremental dirty-chunk saving (B3) shrinks this too.

- `src/main/java/live/minehub/polarpaper/commands/GCCommand.java:18` | **LOW-MEDIUM** | `System.gc()` requested on main thread. | Stop-the-world full collection: typically 50 ms–1 s pause depending on heap/GC. | Run from an async scheduler task, or drop the command (admins have better tooling).

- `src/main/java/live/minehub/polarpaper/commands/UsageCommand.java:70-84` | **LOW-MEDIUM** | Timer task calls `WorldUsage.measure` (walks every holder × 24 sections × nibble arrays, `WorldUsage.java:91-110`) every 10 ticks for 30 s, on main. | ~1–3 ms/tick recurring on multi-thousand-chunk worlds while active; small but pure waste. | Measure once per second max, or compute once and decay; cache per-world between refreshes.

- `src/main/java/live/minehub/polarpaper/commands/BrowseCommand.java:59-72` | **LOW** | `Files.list(parent)` + `Files.isDirectory` stat per entry (twice: comparator + render) executed per page view on main thread. `PolarCmd.listSavedWorldNames:118-133` has a 5 s cache but Browse doesn't reuse it. | Sub-ms to few-ms hitches with many folders/files; minor. | Reuse the cached listing; stat once per path.

### B2. Threading correctness

- `paper_latest/src/main/java/live/minehub/polarpaper/paper_latest/EntitySerializerImpl.java:52-96` (+ `paper_26_1_2` twin) called from `src/.../util/EntitiesWorldAccess.java:113-129` via `PolarChunk.buildChunk` off-main (`PolarChunk.java:240-242`) | **CRITICAL** | Live NMS entities are serialized (`nmsEntity.saveAsPassenger`) on a `commonPool` thread while the entity ticks on its owning thread. The code's own comment admits failure mode ("sometimes calls events... causing errors when called async") and papers over it with try/catch-retry-on-main. First attempt racing tickers can produce torn NBT that serializes *successfully*. Additionally `saveChunkData` blocks with `entityFuture.join()` per entity on a pool thread; the retry path blocks up to **10 s per entity** (`EntitySerializer.SAVE_TIMEOUT_SECONDS`) waiting for main-thread work. | Corrupt saved entities under load; save stalls up to 10 s/entity when the retry triggers; `commonPool` threads parked on joins starve other queued stages. | Serialize on the owner thread in batches (entities were already captured into a snapshot array on main — serialize them there too, bounded per tick), or hand the whole batch to one main-thread task. Never `join()` inside pool tasks.

- `core/.../world/PolarChunk.java:384-398, 506-525` | **CRITICAL** | `buildChunk`'s doc says "reads nothing live", but `convertSection → readSectionLight` reads live starlight `DataLayer`s (`lightEngine.getLayerListener(...).getDataLayerData(...)`) from the pool thread, then clones them. Starlight owns those layers and mutates them during relight; unsynchronized concurrent read+clone can tear. Same class of issue as the entity case but cheaper to fix. | Rarely-corrupt saved light (visual glitches persisting across restarts); hard-to-reproduce. | Copy block/sky light layers inside `snapshotChunk` (main thread) alongside section storage; keep `buildChunk` purely on the snapshot.

- `ForkJoinPool.commonPool()` used as default executor for heavy stages: `Polar.java:184,218` (`thenComposeAsync` streaming whole worlds), `Polar.java:309` (`supplyAsync` claim+parse), `Polar.java:838` (`thenAcceptAsync` doing Zstd compress **and file IO**), `PolarChunk.java:241` (`thenApplyAsync` buildChunk incl. blocking joins), `PolarStreamLoader.java:322` (`runAsync` heightmaps), `ConvertCommand.java:114`, `CreateFromRegionCommand.java:73` | **HIGH** | `commonPool` is sized cores−1, is intended for CPU parallelism, and has no lifecycle. Here it carries: whole-file reads/writes (IO), 10-s-bounded blocking waits, and full-world parses. Concurrent operations (autosave + manual save + convert + loadChunk purchases + SaveZSTDCommand's 23 saves) oversubscribe it; blocked joins (B2 first item) park the very threads needed to progress heightmap/chunk-build stages → pipeline-wide stalls; autosaves start skipping. Also nothing shuts it down (no leak, but also no backpressure or naming/diagnostics). | Intermittent multi-second save/load latency, skipped autosaves, hard-to-diagnose stalls. | Create one dedicated `ExecutorService` (bounded, named, e.g. 2 IO + n CPU threads) owned by the plugin; pass it explicitly to every `*Async` call; shut down in `onDisable` after awaiting saves. Replace internal `join()`s with `thenCompose`.

- `SaveZSTDCommand.java:63-81` | **MEDIUM** | Loop fires `Polar.saveWorld(...)` without awaiting the returned future (timings measure scheduling only — output numbers are meaningless), while mutating the shared `generator.setConfig(compressionLevel=i)` between launches: saves read whichever level was current mid-flight. Up to 23 overlapping full conversions+writes. | Broken benchmark output; minutes of duplicate CPU; GB-scale transient allocations (OOM risk); config race produces wrong-level measurements. | Chain sequentially with `.thenCompose`, measure inside the completion, restore config after.

- `core/.../generator/PolarGenerator.java:24-25` (`config`, `source`), `core/.../generator/PolarStreamingGenerator.java:18-20` (`version`, `dataVersion`, `userData`), `core/.../source/BytesPolarSource.java:5` | **MEDIUM** | Plain non-volatile fields written from main thread (`setConfig` in reload/updateConfig/savezstd; `setSource` in CopyCommand) and from pool threads (`setUserData/setVersion` inside `stream()`), then read cross-thread by the save pipeline (`getConfig().compressionLevel()`, `getVersion()` in `loadChunk`). | Mostly-benign JMM data race: a save can observe stale compression level/source; `loadChunk` can see null version briefly after load. Low probability, real race. | Mark fields `volatile` (they're tiny, written rarely).

- Not found (checked): executor leaks (no manual executors exist), virtual-thread pinning (no vthreads), double-checked locking, unsynchronized world maps (`PolarWorld.chunks` and archive sets are CHM/COW — sound). The archive claim/release protocol (`PolarChunkArchive.java:71-112`) is carefully done.

### B3. Save pipeline throughput

- No dirty-chunk tracking anywhere in the save path: every autosave converts **all** live chunks (`PolarWorld.convert:280-283` enumerates every holder), repacks palettes, recompresses the entire file, rewrites the whole `.polar` atomically — even if nothing changed. Ironically the machinery exists (`tryMarkSaved` is called on insert; moonrise tracks persistence state). | **HIGH** | Periodic CPU burn ∝ loaded chunks + full-file IO/compress every interval; combined with B1 this is the recurring TPS tax of running the plugin. | Track converted-at-tick per position (or reuse moonrise save marks); convert only changed chunks; carry unchanged bodies through the archive snapshot (the `Snapshot.readBodies` mechanism already supports body pass-through verbatim).

- `PolarChunkArchive.readSourceIndex` / `openSource` (`PolarChunkArchive.java:159-192`) run on **every** save (`snapshotIncluding`) and every `loadChunk` claim: full `readBytes` + full Zstd decompress + header-walk of every chunk. The doc comment acknowledges the old double-decompress; a single decompress per save is still O(file) repeated forever. | **MEDIUM-HIGH** | Off-thread CPU/IO per autosave and per plot purchase; latency for buyers; transient 2× file heap each time. | Cache the `SourceIndex` (and raw bytes) alongside the bound source; invalidate in `bindSource`/after `saveBytes`. Consecutive autosaves between edits then cost ~nothing.

- `PolarWriter.write:46-83` | **MEDIUM** | Eager `Unpooled.buffer(estimate)` up to **128 MB** zero-filled upfront (`estimateContentBytes` cap, line 29), then `outputArray` copy, then compressed copy, then header-buffer copy ≈ 3–4× file size in transient allocations per save. Whole-file buffering also caps world size at heap. | GC spikes and allocation-rate blowups on every save of big worlds; save latency scales with copies. | Grow the content buffer adaptively (or track final offset and allocate once post-write); stream compress with `ZstdOutputStreamNoFinalizer` directly into the output byte[]/file to eliminate two copies.

- Compression defaults: `DEFAULT_COMPRESSION_LEVEL = 7` (`PolarWorld.java:47`, surfaced in `Config.java:91`) applied on the hot autosave path (`PolarWriter.java:72`); `PolarChunkStore.read:62` additionally recompresses every chunk at open time (zstd-3) just to hold them compressed in memory. | **MEDIUM** | Level 7 costs roughly 2–4× the CPU of 3 for marginal size win on typical terrain; store-open doubles load CPU for no benefit until eviction. | Default periodic saves to 3–5, reserve high levels for one-shot export/convert; make `PolarChunkStore` keep raw slices and compress lazily on eviction.

### B4. Load pipeline latency

- `Polar.createWorld(source...)` streams the whole world from a single `thenComposeAsync` stage on **one** `commonPool` thread: parse + section creation are sequential; only heightmap priming fans out (`prepareChunkAsync`). For LOAD_EVERYTHING worlds with tens of thousands of chunks, load throughput ≈ one core. | **MEDIUM** | Long world-load times (seconds→tens of seconds) where 2–4 workers would cut wall-clock proportionally; main-thread insert queue drains fine since inserts are cheap. | Split chunk parsing/building across the dedicated CPU executor (sections are independent once the shared `ByteBuf` reader index is handled — slice bodies per chunk first, like `PolarChunkArchive.SourceIndex` already does), keep main-thread insertion serialized.

- `loadEmptyChunk`/`loadChunk` paths are well staged (async prepare → sync insert). `retainChunk` correctly defers ticket acquisition to next tick. No redundant decompression within a single load (one `PolarContentReader.open` per stream). Good.

### B5. Startup / shutdown

- `PolarPaper.onEnable:43-65` | **LOW** | `mkdirs`, `saveDefaultConfig`, depth-4 `Files.walk` with `FOLLOW_LINKS` on main thread at enable; world creation itself (`initSupplier`) is synchronous per world on main (inherent to Bukkit), though actual data streaming is properly off-thread afterwards. | Milliseconds; acceptable. | Drop `FOLLOW_LINKS` (symlink loop protection only needs depth limit); nothing else worth changing.

- Config-write flush ordering is handled correctly: `PENDING_CONFIG` coalescing + `flushPendingConfig` at end of `onDisable` (`Polar.java:636-681`, `PolarPaper.java:122`); atomic moves everywhere (`writeAtomically`, `FilePolarSource.saveBytes`). Worlds are saved before any close. Main residual risks are the in-flight-autosave race (B1) and `updateConfig` being documented "must be synchronous" but invoked from the async completion path in `startAutoSaveTask` (`Polar.java:559` runs it on the timer = main thread — actually correct; keep an eye on future refactors).

## C. Positive notes (keep these)

- Two-phase convert (main-thread snapshot → off-thread build) is the right architecture — it just needs amortizing (B1) and the light copy moved into phase 1 (B2).
- Archive claim/release protocol prevents the classic sold-chunk-vanishes bug; `snapshotIncluding` orphan recovery is thoughtful.
- Atomic temp+move writes for both world files and config; save-failure leaves previous file intact.
- `LOADING_WORLDS` guard blocks saves during streaming; conversion timeout (`CHUNK_CONVERSION_TIMEOUT_MINUTES`) prevents infinite pending saves.
- `PolarCmd` suggestion cache avoids per-keystroke disk hits; `updateConfig` skips rewriting unchanged YAML.
